# PresensiKu — WAF Validation Lab

**PT DrishtiSec**  
**PresensiKu — Controlled Web Application Security Validation**

PresensiKu is an intentionally vulnerable web application designed for controlled security testing, Web Application Firewall (WAF) validation, application-side behavior analysis, evidence collection, and security reporting.

The project is built around a practical validation workflow: security findings observed in WAF logs can be replayed against an isolated application, validated at the application/server layer, and correlated with technical evidence.

> **Scope:** This project is intended for authorized security testing, research, training, and isolated laboratory environments only.

---

## Overview

The lab simulates a corporate employee attendance application operated by **PT DrishtiSec**.

The application provides a realistic business-oriented interface while containing controlled vulnerabilities that can be used to study:

- How attack requests reach application endpoints
- How vulnerable backend processing behaves
- What impact can be observed at the application/server layer
- How WAF detection can be correlated with application-side validation
- How technical evidence can be documented for security reporting

The application uses **synthetic data** and isolated laboratory resources.

---

## Objectives

The main objectives of this project are to:

- Validate WAF detection and blocking behavior
- Replay representative attack requests against a controlled application
- Validate whether an observed request can reproduce vulnerable application behavior
- Study the relationship between HTTP requests and backend processing
- Collect request, response, and server-side evidence
- Correlate WAF observations with application-side validation
- Document findings and remediation guidance
- Practice a complete security validation workflow from discovery to reporting

## Validation Workflow

The lab follows a practical workflow:

```text
WAF Evidence
     │
     ▼
Request Review
     │
     ▼
Application Discovery
     │
     ▼
Endpoint / Parameter Discovery
     │
     ▼
Normal Request
     │
     ▼
Security Testing
     │
     ▼
Controlled Request Replay
     │
     ▼
Application / Server Behavior
     │
     ▼
Evidence Collection
     │
     ▼
WAF Correlation
     │
     ▼
Remediation
```

The purpose is to distinguish **WAF detection** from **validated application impact**.

A WAF alert by itself is not treated as proof of successful exploitation. The laboratory validates the request against the application and records the resulting behavior separately.

## Validation Scenarios

The current application contains controlled scenarios covering:

### 1. Command Injection

Demonstrates insecure handling of command input and controlled server-side command execution behavior.

### 2. Local File Inclusion (LFI)

Demonstrates insecure file inclusion behavior and controlled exposure of application-side file content.

### 3. Directory Traversal

Demonstrates path manipulation that can cause unintended access to files outside the expected application directory.

### 4. Reflected Cross-Site Scripting (XSS)

Demonstrates reflected input reaching the HTTP response without appropriate output encoding.

### 5. SQL Injection — UNION Based

Demonstrates vulnerable SQL query construction and UNION-based result manipulation through the application search functionality.

The scenario is designed so the vulnerable query layer can reproduce the structure of a controlled validation request and expose the resulting database response in the application.

### 6. Unrestricted File Upload / Web Shell

Demonstrates insecure file upload handling in a controlled laboratory environment, including server-side handling of uploaded script files.

## Evidence Model

Security validation separates evidence into three layers:

### WAF Evidence

The original request/observation captured by the WAF source.

### POC Evidence

The controlled replay and the resulting application behavior.

### Server / Application Evidence

Evidence generated by the target application, backend processing, logs, database execution, or controlled filesystem artifacts.

This separation helps answer:

> **What did the WAF observe?**  
> **What did the application actually process?**  
> **What impact could be reproduced in the controlled environment?**

## Running the Application

Create and activate a Python virtual environment:

```bash
python3 -m venv .venv
source .venv/bin/activate
```

Install the project dependencies:

```bash
pip install -r requirements.txt
```

Start the Flask application using the project's configured entry point.

For a local laboratory deployment, access the application from the assigned lab address and port.

> Keep the vulnerable application isolated from production systems and untrusted networks.
